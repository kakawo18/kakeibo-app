# Claude 連携（リモート MCP サーバー）実装手順書

- 状態: PR 1〜4 を実装（v6.7.0〜v6.8.0）
- 作成: 2026-10-22
- 仕様: [仕様書.md](./仕様書.md)（先に読む）

この手順書は、仕様書で決めた Claude 連携を、どの順に作り、各段階をどう確かめるかを書いたものである。コードは形を示すための抜粋で、そのまま貼れば動くものではない。ライブラリの API は版で変わるので、実装のときに各ライブラリの資料と型定義で確かめる。

## 1. 進め方

作業は4つの PR に分ける。PR 1 と PR 2 は本番に入っても利用者から見える変化が無いので、そこで止めても本番は壊れない。

| PR | 内容 | 利用者に見える変化 | バージョン |
|----|------|--------------------|------------|
| 1 | サーバー側の読み出し層。予算の計算を domain へ移す | なし | 上げない |
| 2 | MCP のツール（開発環境のエミュレータでだけ動く） | なし | 上げない |
| 3 | 認可サーバーと本番での有効化 | Claude から接続できるようになる | minor |
| 4 | 設定画面の接続の解除とドキュメント | 設定画面に欄が増える | patch |

どの PR でも、コミットの前に次を通す（AGENTS.md の決まり）。

```bash
npm run lint
npm run type-check
npm test
npm run test:emulator   # Java 21 が必要
```

Route Handler やページを書く前には、`node_modules/next/dist/docs/` の該当する資料（Route Handler、`searchParams`、`instrumentation`）を読む。この Next.js は 16 で、学習データにある書き方と違うところがある。

## 2. 事前の準備（人が行う作業）

コードを書く前に、Firebase と Vercel の画面で行う作業をまとめる。2.5 節の環境変数の登録は PR 3 を本番に出す直前でよいが、値は先に用意しておく。

### 2.1 本番の URL を決める

Claude に登録する URL と、トークンの aud（宛先）に、本番の URL が入る。後で URL を変えると、全員がコネクタを登録し直すことになる。Vercel が発行した `*.vercel.app` のままでも動くが、変わる予定があるなら先に独自ドメインを付けておく。決めた URL を `MCP_PUBLIC_ORIGIN` にする（例 `https://kakeibo.example.com`。末尾のスラッシュは付けない）。

Vercel の Deployment Protection（Vercel Authentication）が本番にかかっていると、Claude からの通信も止められる。Vercel のプロジェクト設定 → Deployment Protection で、本番が保護の対象外になっていることを確かめる。

### 2.2 サービスアカウントを作る

Admin SDK が使う、権限を絞ったサービスアカウントを作る。Firebase Console の「サービスアカウント」タブから作る鍵は、プロジェクトのほぼすべてを操作できる権限を持つので使わない。

1. Google Cloud Console で、Firebase と同じプロジェクトを選ぶ。
2. 「IAM と管理」→「サービスアカウント」→「サービスアカウントを作成」。名前は `kakeibo-mcp` など。
3. ロールに次の2つを付ける。
   - Cloud Datastore ユーザー（`roles/datastore.user`）: Firestore の読み書き
   - （v6.7.2 から不要）Firebase Authentication 閲覧者（`roles/firebaseauth.viewer`）: 当初は ID トークンの失効の確認に使う予定だったが、検証を `jose` に替えたので使わない。付けてしまっていても害は無いが、外してよい
4. 作ったアカウントの「鍵」→「鍵を追加」→「新しい鍵を作成」→ JSON。ファイルがダウンロードされる。
5. 環境変数に入れるため、1行の base64 にする。

```bash
base64 -w0 kakeibo-mcp-xxxx.json   # macOS は base64 -i kakeibo-mcp-xxxx.json
```

鍵のファイルはリポジトリの中に置かず、環境変数に登録したら削除する。

### 2.3 使ってよい uid を調べる

Firebase Console →「Authentication」→「ユーザー」で、Claude 連携を使う人の「ユーザー UID」を控える。複数ならカンマでつなぐ。これが `MCP_ALLOWED_UIDS` になる。

### 2.4 秘密の値を作る

```bash
openssl rand -base64 48                        # MCP_TOKEN_SECRET
echo "kakeibo-claude-$(openssl rand -hex 8)"   # MCP_OAUTH_CLIENT_ID
```

### 2.5 Vercel に環境変数を登録する

Vercel のプロジェクト設定 → Environment Variables で、仕様書 9章の6つを登録する。対象の環境は Production だけにする（Preview と Development には入れない）。`MCP_ENABLED` は PR 3 を本番に出すときに `1` にし、それまでは登録しないでおく。

### 2.6 Firestore の TTL（不要。有料プランのみ）

当初はここで TTL ポリシーを作り、期限の切れたコードとトークンを自動で消す予定だった。TTL は無料プランでは使えないので、v6.8.0 からはトークンを発行するたびにアプリの側で消している（仕様書 5.9 節）。有料プランで TTL を使う場合は、次の2つのポリシーを作ってもよい（あっても害は無い）。

| コレクション グループ | タイムスタンプのフィールド |
|-----------------------|----------------------------|
| `oauthAuthorizationCodes` | `expiresAt` |
| `oauthRefreshTokens` | `expiresAt` |

### 2.7 Firestore の複合インデックスを作る

get_kakeibo_overview は最も古い取引を引くために、取引を日付の古い順（`userId` 昇順 + `date` 昇順）で読む。アプリの画面は新しい順（`date` 降順）でしか読まないので、このインデックスは既存のプロジェクトには無い。エミュレータはインデックスを要求しないので、テストでは気づけない。

インデックスの定義はリポジトリの `firestore.indexes.json` にある。Firebase Console →「Firestore Database」→「インデックス」→「複合」→「インデックスを作成」で、次の内容で作る（または `firebase deploy --only firestore:indexes`）。

| 項目 | 値 |
|------|----|
| コレクション ID | `transactions` |
| フィールド 1 | `userId`・昇順 |
| フィールド 2 | `date`・昇順 |
| クエリのスコープ | コレクション |

作成には数分かかる（状態が「ビルド中」から「有効」になる）。インデックスが無い間も概要のほかの項目は返り、記録のある期間だけが空になる（v6.7.3）。

### 3.5 読み出し（src/server/kakeiboReader.ts）

仕様書 7.2 節の規則に従って書く。uid は必ず最初の引数で受け取り、クエリの最初で絞る。

```ts
import 'server-only';
import { Timestamp } from 'firebase-admin/firestore';
import { adminDb } from './firebaseAdmin';
import { fromTransactionDoc } from '@/data/transactionSerializer';
import type { Transaction } from '@/types';

/** uid の取引のうち、from 以上 before 未満の日付のもの */
export const readTransactions = async (
  uid: string,
  range: { from: Date; before: Date }
): Promise<Transaction[]> => {
  const snapshot = await adminDb
    .collection('transactions')
    .where('userId', '==', uid)
    .where('date', '>=', Timestamp.fromDate(range.from))
    .where('date', '<', Timestamp.fromDate(range.before))
    .orderBy('date', 'desc')
    .get();

  return snapshot.docs.flatMap((doc) => {
    const data = doc.data();
    // ルールを通らないので、所有者をもう一度確かめる（仕様書 7.2）
    if (data.userId !== uid) {
      console.error('kakeiboReader: userId mismatch', doc.id);
      return [];
    }
    const transaction = fromTransactionDoc(doc.id, data);
    return transaction ? [transaction] : [];
  });
};
```

同じファイルに次の関数を足す。

- `readRecordedPeriod(uid)`: `orderBy('date', 'asc').limit(1)` と `orderBy('date', 'desc').limit(1)` で最も古い取引と最も新しい取引の日付を返す
- `readSettings(uid)`: `users/{uid}/settings/app` を読み、`deserializeSettings` で変換する。ドキュメントが無ければ、「アプリを一度開いて設定を作ってください」という説明つきのエラーにする
- `readRecurringTransactions(uid)`: `users/{uid}/recurringTransactions` を読み、`fromRecurringDoc` で変換する

## 4. PR 2: MCP のツール

この PR では MCP の受け口とツールを作る。本番では `MCP_ENABLED` が未設定なので 404 を返し、開発環境ではエミュレータのデータに対してだけ認証なしで動かす。

### 4.1 依存を足す

```bash
npm install mcp-handler@^2 @modelcontextprotocol/server@^2 zod@^4
```

mcp-handler 2.x は `@modelcontextprotocol/server` 2.x・zod 4.2 以上・Node.js 20 以上を求める。1.x の資料（`basePath`・`maxDuration`・`redisUrl`・`server.tool(...)`）は 2.x では使えないので、検索で見つけた記事の書き方を写さない。

### 4.2 ツールを「読む部分」と「組み立てる部分」に分ける

各ツールは、Firestore から読む部分と、読んだ取引と設定から結果を組み立てる部分に分ける。組み立てる部分は Firestore に依存しない純関数にして、`npm test` で確かめられるようにする。

```
src/server/mcp/
  registerTools.ts            全ツールの登録
  instructions.ts             サーバーの説明文（仕様書 6.8）
  context.ts                  認証情報から uid を取り出す
  tools/
    monthlySummary.ts         入力スキーマ・説明文・読む範囲・組み立て
    monthlySummary.test.ts    組み立て部分のテスト（fixtures を使う）
    searchTransactions.ts
    ...
```

ツールの登録は次の形になる。

```ts
server.registerTool(
  'get_monthly_summary',
  {
    title: '月の収支',
    description: '指定した月（既定は今月）の収入・支出・収支、前月比、カテゴリ別の内訳、月間予算との比較を返す。金額は円。支出からは投資と立替金を除いている。',
    inputSchema: z.object({
      month: z.string().regex(/^\d{4}-(0[1-9]|1[0-2])$/).optional(),
    }),
    annotations: { readOnlyHint: true },
  },
  async ({ month }, ctx) => {
    assertJapanTime();
    const uid = uidFrom(ctx);            // ctx.http?.authInfo?.extra?.uid
    const target = month ?? getCurrentMonth();
    const [settings, transactions] = await Promise.all([
      readSettings(uid),
      readTransactions(uid, monthlySummaryRange(target)),
    ]);
    const result = buildMonthlySummary(transactions, settings, target);
    return { content: [{ type: 'text', text: JSON.stringify(result) }] };
  }
);
```

組み立ての関数（例 `buildMonthlySummary`）の中で `createTransactionRules(settings)` を作り、仕様書 6章の表にある domain の関数を呼ぶ。テストでは、同じ取引を渡したときに画面と同じ数値（`calculateMonthlyData` などの結果）になること、改名前のカテゴリ名の取引が今の名前で数えられること、search_transactions の totals が limit で切る前の全件の合計であることを確かめる。

### 4.3 受け口（src/app/api/mcp/route.ts）

```ts
import { createMcpHandler, withMcpAuth } from 'mcp-handler';
import { isMcpEnabled } from '@/server/config';
import { registerKakeiboTools } from '@/server/mcp/registerTools';
import { KAKEIBO_INSTRUCTIONS } from '@/server/mcp/instructions';
import { isDevBypass, verifyMcpToken } from '@/server/oauth/verifyMcpToken';
import packageJson from '../../../../package.json';

export const runtime = 'nodejs';

const handler = createMcpHandler((server) => registerKakeiboTools(server), {
  serverInfo: { name: 'kakeibo', version: packageJson.version },
  instructions: KAKEIBO_INSTRUCTIONS,
});

const authHandler = withMcpAuth(handler, verifyMcpToken, {
  required: true,
  requiredScopes: ['kakeibo.read'],
});

const route = (request: Request) =>
  isMcpEnabled() || isDevBypass() ? authHandler(request) : new Response(null, { status: 404 });

export { route as GET, route as POST };
```

`instructions` を options に渡せるかは、mcp-handler の型（`McpHandlerOptions` が `ServerOptions` を含む）で確かめる。

### 4.4 開発用の認証の省略

PR 2 の時点では認可サーバーが無いので、開発環境でだけ認証を省く。省いてよい条件は、`NODE_ENV === 'development'` で、かつ `FIRESTORE_EMULATOR_HOST` が設定されていることの両方とする。この二つがそろうのはローカルでエミュレータにつないでいるときだけなので、本番のデータを認証なしで読む経路にはならない。

```ts
// src/server/oauth/verifyMcpToken.ts（PR 2 の時点）
export const isDevBypass = () =>
  process.env.NODE_ENV === 'development' && Boolean(process.env.FIRESTORE_EMULATOR_HOST);

export const verifyMcpToken = async (_req: Request, bearerToken?: string): Promise<AuthInfo | undefined> => {
  if (isDevBypass() && process.env.MCP_DEV_UID) {
    return { token: bearerToken ?? 'dev', clientId: 'dev', scopes: ['kakeibo.read'], extra: { uid: process.env.MCP_DEV_UID } };
  }
  return undefined; // PR 3 で本物の検証に置き換える
};
```

### 4.5 ローカルで確かめる

1. `.env.local` に次を足す。`MCP_DEV_UID` は、エミュレータの Authentication で作ったテスト用のユーザーの uid である。

   ```
   NEXT_PUBLIC_FIREBASE_EMULATOR=1
   FIRESTORE_EMULATOR_HOST=127.0.0.1:8080
   MCP_DEV_UID=（エミュレータのテストユーザーの uid）
   ```

2. エミュレータとアプリを起動する。

   ```bash
   npx firebase-tools@13 emulators:start --only auth,firestore --project （NEXT_PUBLIC_FIREBASE_PROJECT_ID の値）
   npm run dev
   ```

   エミュレータのプロジェクト ID は、アプリ（クライアント SDK）と Admin SDK の両方が使う `NEXT_PUBLIC_FIREBASE_PROJECT_ID` にそろえる。ずれると、アプリで入れたデータを Admin SDK が別のプロジェクトとして読み、0件に見える。

3. アプリにテストユーザーでログインし、数か月分の架空の取引を入れる（CSV の取り込みを使うと早い）。本番の家計データは使わない。
4. MCP Inspector を起動し、`http://localhost:3000/api/mcp` に Streamable HTTP でつなぐ。

   ```bash
   npx @modelcontextprotocol/inspector
   ```

   ツールの一覧に6つが並び、各ツールに読み取り専用の印が付いていることを確かめる。get_monthly_summary を呼び、アプリのホームの同じ月の収入・支出・収支・カテゴリ別と一致することを確かめる。

5. チャットの形でも試せる。Claude Code はローカルの HTTP の MCP サーバーにつなげるので、次のように登録して「先月の食費は？」などと聞く。

   ```bash
   claude mcp add --transport http kakeibo-local http://localhost:3000/api/mcp
   ```

   ツールの説明文が分かりにくいと、Claude が違うツールを呼んだり期間を取り違えたりする。ここで説明文を直しておくと、本番で直すより手間が少ない。

## 5. PR 3: 認可サーバーと本番での有効化

### 5.1 依存を足す

```bash
npm install jose
```

### 5.2 OAuth の部品（src/server/oauth/）

| ファイル | 中身 | テスト |
|----------|------|--------|
| `params.ts` | 認可リクエストのパラメータの検証（仕様書 5.5 節の表） | 単体 |
| `pkce.ts` | `code_verifier` と `code_challenge` の照合 | 単体 |
| `random.ts` | 32バイトの乱数と sha256 のハッシュ | 単体 |
| `accessToken.ts` | JWT の発行と検証（仕様書 5.8 節） | 単体 |
| `codes.ts` | 認可コードの保存と、トランザクションでの読み出しと削除 | エミュレータ |
| `refreshTokens.ts` | 発行・ローテーション・再使用の検出・uid ごとの削除 | エミュレータ |
| `verifyMcpToken.ts` | `withMcpAuth` に渡す確認関数（仕様書 5.11 節） | 単体 |

PKCE の照合は次の形になる。`code_verifier` は 43〜128 文字の `[A-Za-z0-9-._~]` だけを受け付ける。

```ts
import { createHash, timingSafeEqual } from 'node:crypto';

export const verifyPkce = (verifier: string, challenge: string): boolean => {
  if (!/^[A-Za-z0-9\-._~]{43,128}$/.test(verifier)) return false;
  const computed = Buffer.from(createHash('sha256').update(verifier).digest('base64url'));
  const expected = Buffer.from(challenge);
  return computed.length === expected.length && timingSafeEqual(computed, expected);
};
```

テストには RFC 7636 の付録にある例を使う。verifier `dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk` から challenge `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM` が得られる。

アクセストークンの検証は次の形になる。

```ts
import { jwtVerify } from 'jose';

const { payload } = await jwtVerify(bearerToken, config.tokenSecret, {
  issuer: config.origin,
  audience: config.resource,
  algorithms: ['HS256'],
});
```

単体テストでは、aud の違うトークン・期限切れのトークン・別の鍵で署名したトークン・`alg: none` のトークン・許可リストに無い uid のトークンが、すべて拒否されることを確かめる。

### 5.3 メタデータの Route Handler

保護リソースのメタデータ（`src/app/.well-known/oauth-protected-resource/route.ts`）は mcp-handler の部品で返す。

```ts
import { metadataCorsOptionsRequestHandler, protectedResourceHandler } from 'mcp-handler';

const handler = protectedResourceHandler({ authServerUrls: [mcpConfig().origin] });
const corsHandler = metadataCorsOptionsRequestHandler();
export { handler as GET, corsHandler as OPTIONS };
```

返ってくる `resource` が `{origin}/api/mcp` になっているかを、ローカルで `curl` して確かめる。ライブラリがリクエストの URL から組み立てて別の値になる場合は、この Route Handler では自前で JSON を返す。

認可サーバーのメタデータ（`src/app/.well-known/oauth-authorization-server/route.ts`）は、仕様書 5.3 節の JSON を `mcpConfig()` の値から組み立てて返す。どちらも `isMcpEnabled()` でないときは 404 にする。

### 5.8 firestore.rules

`oauthAuthorizationCodes` と `oauthRefreshTokens` を名指しで拒否するルールを足す。冒頭の「データ構成」のコメントにも、この2つと「Admin SDK だけが読み書きする」ことを書き足す。

`src/data/repositories.emulator.test.ts` か新しいエミュレータのテストに、ログインした利用者でもこの2つを読めない・書けないことを確かめるテストを足す。本番に出すときは `firebase deploy --only firestore:rules` で反映する。

### 5.9 エミュレータのテスト

`src/server/oauth/*.emulator.test.ts` に次を書く。

- 認可コードは1回しか交換できない。2回目は `invalid_grant`
- 期限の切れたコードは交換できない
- PKCE の verifier が違えば交換できない
- リフレッシュトークンで更新すると新しいトークンが返り、古いトークンは使えなくなる
- 古いトークンを60秒より後に使うと、同じ familyId のトークンがすべて消える
- 60秒以内の再使用では、ファミリーは消えない
- 利用者 A の接続を解除しても、利用者 B のトークンは残る

### 5.10 ローカルで OAuth の流れを通す

claude.ai はローカルの開発サーバーに届かないので、ローカルでは手作業で流れを通す。開発環境でだけ、redirect_uri に `http://localhost:9999/callback` を追加で許可する（4.4 節と同じ条件で有効にする）。

1. verifier と challenge を作る。

   ```bash
   VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
   CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -sha256 -binary | base64 | tr '+/' '-_' | tr -d '=')
   ```

2. ブラウザで次の URL を開き、ログインして許可する。

   ```
   http://localhost:3000/oauth/authorize?response_type=code&client_id=（MCP_OAUTH_CLIENT_ID）&redirect_uri=http://localhost:9999/callback&code_challenge=（CHALLENGE）&code_challenge_method=S256&state=test
   ```

   9999番では何も待ち受けていないので、ブラウザは接続エラーになる。アドレスバーの `code=` の値を控える。

3. トークンと交換する。

   ```bash
   curl -s http://localhost:3000/api/oauth/token \
     -d grant_type=authorization_code -d code=（控えた code） \
     -d redirect_uri=http://localhost:9999/callback \
     -d client_id=（MCP_OAUTH_CLIENT_ID） -d code_verifier="$VERIFIER"
   ```

4. 返ってきた access_token を MCP Inspector の認証の欄（Bearer トークン）に入れてつなぎ、ツールが呼べることを確かめる。トークンなしでは 401 になることも確かめる。
5. refresh_token で更新し（`-d grant_type=refresh_token -d refresh_token=... -d client_id=...`）、同じ refresh_token を2回目に使うと `invalid_grant` になることを確かめる。

## 8. 運用

### 8.1 止めたいとき

仕様書 5.10 節の表のとおり。急ぐときは Vercel で `MCP_ENABLED` を消して再デプロイ（Redeploy）すれば、すべてのエンドポイントが 404 になる。

### 8.2 鍵を替える

- サービスアカウントの鍵は年に一度を目安に替える。Google Cloud Console で新しい鍵を作り、Vercel の `FIREBASE_SERVICE_ACCOUNT_KEY` を替えて再デプロイし、動作を確かめてから古い鍵を削除する。
- `MCP_TOKEN_SECRET` を替えると、発行済みのアクセストークンはすべて無効になる（リフレッシュトークンは残るので、Claude は1回の更新で戻る）。漏えいが疑われるときは、リフレッシュトークンも全件削除する。

### 8.3 ログ

Vercel の Functions のログには `console.error` だけが残る（本番では他の console は除かれる）。ログに出すのは、ツールの名前・エラーの種類・ドキュメントの ID までにする。トークン・ID トークン・取引の中身・ツールの入力（検索の語にも家計の情報が含まれうる）は出さない。

### 8.4 依存の更新

MCP の仕様と mcp-handler の版を半年に一度ほど確かめる。Claude の対応している認可仕様の版が変わったら、仕様書 11章の前提が崩れていないかを見直す。

## 9. うまくいかないとき

| 症状 | 確かめること |
|------|--------------|
| コネクタを追加しても接続できない | URL が `/api/mcp` まで含んでいるか。`MCP_ENABLED` が Production に設定されているか。Deployment Protection が本番にかかっていないか（2.1 節） |
| 同意画面がエラーになる | Claude に入れた client ID が `MCP_OAUTH_CLIENT_ID` と一致するか。Vercel のログに出た検証の失敗の種類 |
| 許可した後に Claude 側でエラーになる | トークンのエンドポイントのログ。メタデータの `issuer` が `MCP_PUBLIC_ORIGIN` と完全に一致するか。`resource` の不一致（`invalid_target`）。応答が10秒以内に返っているか |
| 「自分の OAuth クライアントを使う」が見つからない | Claude の画面が変わった可能性がある。資料で確かめ、無くなっていれば DCR に対応する（下記） |
| 1時間ほどで使えなくなる | リフレッシュトークンの更新が失敗している。再使用の検出でファミリーが消えていないか（ログに出す種類で分かるようにしておく） |
| `/api/mcp`・`/api/oauth/token`・同意画面だけが 500（メタデータは返る） | Vercel のログに `ERR_REQUIRE_ESM`（`jwks-rsa` が `jose` を読み込めない）が出ていれば、`firebase-admin/auth`（または `firebase-admin` 全体）を読み込むコードが入った。Vercel の Node.js 22 は ES モジュールの `require()` に対応していない版なので、`firebase-admin/app`・`firebase-admin/firestore` だけを使う（v6.7.2。ESLint でも禁止している） |
| 概要で「記録のある期間を取得できなかった」と出る（v6.7.2 までは概要そのものが「読み出しに失敗しました」） | 複合インデックス（`transactions`: `userId` 昇順 + `date` 昇順）が無い。2.7 節。Vercel のログには `FAILED_PRECONDITION` と、インデックスを作るためのリンクが出る |
| 月の数字が画面とずれる | タイムゾーンの確認（3.3 節）。改名したカテゴリの読み替え。Claude が「先月」を何月と解釈したか（ツールの入力を見る） |
| ツールの結果が途中で切れる | 結果が15万文字に近い。limit を下げるか、集計のツールを使うよう説明文で促す |

事前登録が使えなくなった場合の代わりは、DCR（`/api/oauth/register`）である。登録を受け付けるのは `redirect_uris` が `https://claude.ai/api/mcp/auth_callback` だけのときに限り、登録したクライアントを Firestore に保存する。メタデータに `registration_endpoint` を足す。受け付けるリダイレクト先が1つのままなので、仕様書 4.1 節の「検証する入力の幅を狭くする」方針は保たれる。
