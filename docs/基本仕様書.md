# 基本仕様書

家計簿アプリのシステム全体の仕様をまとめる。個々の画面・機能の詳細は [`機能仕様書.md`](./機能仕様書.md) を参照。
実装の設計判断（「なぜそうなっているか」）は [`architecture.md`](./architecture.md) を参照。本書は現時点（v6.4.4）の実装状態を正としてまとめている。仕様書自体の改訂履歴は [16. 改訂履歴](#16-改訂履歴) にある。

## 1. 目的・概要

個人（1〜少数ユーザー）向けの家計簿 PWA（Progressive Web App）。収入・支出の記録、カテゴリ別の可視化、定期取引の自動提示、クレジットカードの引き落としタイミングを考慮した収支管理、年単位の振り返りを提供する。

- ブラウザからも、ホーム画面に追加したアプリとしても利用できる。
- 複数デバイス間でデータを同期する（Firestore によるリアルタイム同期）。
- 家族・チームでの共有は想定しない。1 Firebase ユーザー = 1 家計簿。

## 2. 用語定義

| 用語 | 意味 |
|---|---|
| 取引（Transaction） | 収入・支出の1件の記録。金額・カテゴリ・日付などを持つ |
| カテゴリ / サブカテゴリ | 取引を分類する単位。ユーザーが自由に追加・編集できる |
| 役割（CategoryRole） | カテゴリ/サブカテゴリに付与する集計上のフラグ（給与収入・投資・立替金など） |
| 定期取引（Recurring Transaction） | 毎月決まった日に発生する取引のテンプレート。実行日以降にワンタップで記録できる |
| 支払方法 | 取引の決済手段（現金・各クレジットカード）。カードには還元率を設定できる |
| 現金扱い | 支払方法の属性。オンなら現金や口座振替など、購入時にその場で決済される方法（＝クレジットカードではない）として扱う |
| 収支 | 選択月の収入合計−支出合計。アプリが計算・表示する唯一の「差引金額」で、実際の銀行口座残高は別概念（アプリでは記録・計算しない）。クレジットカードの支出も購入月の支出として即座に反映される。詳細は [`機能仕様書.md`](./機能仕様書.md#24-クレジットカード払いの会計モデル重要な業務ルール) を参照 |
| 額面 | 手取りに税・社会保険料を足し戻した推定年収（アプリは手取りしか記録しないため概算） |

## 3. 想定利用者・利用環境

- **利用者**: 個人の家計管理者。技術的な前提知識は不要。
- **利用環境**: モダンブラウザ（デスクトップ / モバイル）。768px を境にレイアウトが切り替わる。
- **対応ブラウザ**: 明示的なサポートマトリクスは定めていない。Next.js 16 / Firebase SDK 11 が動作する最新版の Chrome / Safari / Edge / Firefox を想定し、主にモバイル Safari（iOS ホーム画面アプリ）と Chrome で目視確認している。IE・旧版ブラウザは対象外。
- **オフライン**: **オンライン利用が前提で、オフライン動作は保証しない**。実際の挙動は次のとおり。
  - Service Worker（`public/sw.js`）がアプリシェルをキャッシュするため、オフラインでも画面の起動自体は可能（[11.3](#113-レスポンシブ--pwa)）。
  - Firestore の永続キャッシュ（`persistentLocalCache`）は有効化しておらず、SDK 既定のメモリキャッシュのみ。起動中に一度読み込んだ取引はメモリに残るため、**通信が切れた後も開いているタブ内では閲覧できる**が、アプリを再起動するとオフラインでは何も表示されない。
  - オフライン中の書き込みは SDK がローカルに保留し、通信復旧後にサーバーへ送る。保存完了の通知はサーバー確定を待つため、復旧まで表示されないことがある。
- **通貨**: 日本円のみ、小数点以下は切り捨て。
- **多言語対応**: なし（UI は日本語固定）。
- **テーマ**: ライト / ダークの両方に対応。初期値は OS 設定に追従し、ヘッダーのボタンで切り替えられる（[`機能仕様書.md`](./機能仕様書.md#15-テーマ切替ライト--ダーク) 参照）。

## 4. システム構成

```
[ブラウザ / PWA]
   ├─ Next.js (App Router, Turbopack) — フロントエンドのみ。専用のサーバー API 層は無い
   │    └─ Firebase SDK を直接呼び出す
   │
   ├─ Firebase Authentication（メール / パスワード認証）
   └─ Firebase Firestore（データ永続化 + リアルタイム購読）

[Vercel]  — ホスティング / CI・CD。main への push で本番自動デプロイ、PR ごとにプレビュー環境
```

- **サーバーサイド API を持たない**。クライアントが Firestore に直接読み書きするため、アクセス制御は `firestore.rules` のみが担保する（[11.1 セキュリティ](#111-セキュリティ)参照）。
- ビルド・デプロイは Vercel が担当し、Firebase 側はデータベースと認証のみを担う。

### 4.1 環境構成

| 環境 | 実行場所 | Firebase 接続先 | 用途 |
|---|---|---|---|
| ローカル開発 | `npm run dev`（localhost:3000） | `.env.local` の Firebase プロジェクト | 日常の開発・目視確認 |
| ローカル（エミュレータ） | `npm run dev` + `NEXT_PUBLIC_FIREBASE_EMULATOR=1` | Firebase Emulator（Auth: 9099 / Firestore: 8080） | 実データを触らずに検証 |
| Preview | Vercel（PR ごとに自動生成） | Vercel の環境変数に設定した Firebase プロジェクト | PR のレビュー・動作確認 |
| Production | Vercel（`main` ブランチ） | 同上 | 本番 |

- **接続先の Firebase プロジェクトは Vercel の環境変数設定に依存する**。リポジトリ側に環境ごとの切り替え機構は無く、Preview / Production で環境変数を分けていなければ、Preview 環境も本番の Firestore を読み書きする。その場合、Preview で検証用に追加した取引はそのまま本番データに残る。現在の Vercel 設定で分離しているかどうかは本書では確認していない（[15. 既知の課題](#15-既知の課題今後の検討事項) #8）。
- Firebase Authentication のアカウントは Firebase プロジェクトごとに独立している。プロジェクトを切り替えた場合はアカウントも作り直しになる（[`setup.md`](./setup.md#トラブルシューティング) 参照）。

### 4.2 環境変数

すべてクライアントに埋め込まれる公開値（`NEXT_PUBLIC_*`）であり、秘密情報は存在しない。

| 変数 | 必須 | 用途 |
|---|---|---|
| `NEXT_PUBLIC_FIREBASE_API_KEY` | ✓ | Firebase Web SDK 設定 |
| `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN` | ✓ | 同上 |
| `NEXT_PUBLIC_FIREBASE_PROJECT_ID` | ✓ | 同上 |
| `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` | ✓ | 同上（Storage は未使用だが SDK 初期化に渡す） |
| `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID` | ✓ | 同上 |
| `NEXT_PUBLIC_FIREBASE_APP_ID` | ✓ | 同上 |
| `NEXT_PUBLIC_FIREBASE_EMULATOR` | – | `1` でローカルの Firebase エミュレータに接続 |
| `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` | – | 設定時のみ App Check（reCAPTCHA v3）を初期化 |
| `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` | – | Vercel が自動付与。画面下部のコミットSHA表示に使う |

必須変数が未設定でもビルドは通る（`src/lib/firebase.ts` がプレースホルダーで初期化する）が、認証・データ取得は動作しない。設定手順は [`setup.md`](./setup.md)、Vercel 側の登録は [`deployment.md`](./deployment.md) を参照。

## 8. データモデル（Firestore）

サーバー API を持たないため、コレクション構成がそのままアクセス制御の単位になる。

### 8.1 `transactions/{transactionId}`（トップレベルコレクション）

取引データ。所有者は `userId` フィールドで判定する（サブコレクションではない）。

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| userId | string | ✓ | 所有者の UID |
| type | `'income' \| 'expense'` | ✓ | 収入 / 支出 |
| amount | number | ✓ | 金額（円、0以上） |
| category | string | ✓ | カテゴリ名（最大50文字） |
| subcategory | string | – | サブカテゴリ名 |
| paymentMethod | string | – | 支払方法名（支出のみ） |
| transactionType | `'normal' \| 'card_payment' \| 'card_withdrawal'` | – | 取引タイプ（`card_withdrawal` は廃止済みのレガシー値） |
| affectsExpense | boolean | – | 支出集計に含めるか（役割から自動導出） |
| date | timestamp | ✓ | 取引日 |
| description | string | – | メモ |
| createdAt / updatedAt | timestamp | ✓ | システム側で付与 |

上表の「必須」はアプリ（クライアントコード）が常に書き込むフィールドを示す。**Firestore セキュリティルール（`firestore.rules`）が型・必須性を検証するのは `userId` / `type` / `amount` / `category` / `date` のみ**で、`transactionType` / `affectsExpense` / `createdAt` / `updatedAt` / `paymentMethod` の値はルール側では検証しない（[10. 認証・認可](#10-認証認可) 参照）。サーバー API を持たない構成のため、これらのフィールドの整合性はクライアントコードの実装に依存する。

### 8.2 `users/{uid}/settings/app`（ユーザー1人につき1ドキュメント）

| フィールド | 型 | 説明 |
|---|---|---|
| schemaVersion | number | 現在は `1` 固定 |
| monthlyBudget | number | 月間予算（円） |
| categories | CategorySetting[] | 収支カテゴリ・役割・色・サブカテゴリ（配列順=表示順） |
| paymentMethods | PaymentMethodSetting[] | 支払方法・現金フラグ・還元率・色 |
| chartPreferences | object（任意） | グラフ表示設定（比較カテゴリなど） |
| createdAt / updatedAt | timestamp | |

初回ログイン時にドキュメントが存在しなければ自動シードする（取引が既にあるユーザーには旧ハードコード相当の設定、新規ユーザーには汎用デフォルト設定）。詳細は [`architecture.md`](./architecture.md#状態管理) を参照。

### 8.3 `users/{uid}/recurringTransactions/{id}`

| フィールド | 型 | 説明 |
|---|---|---|
| name | string | 表示名 |
| amount | number | 金額 |
| category / subcategory | string | 分類 |
| paymentMethod | string（任意） | 支払方法 |
| dayOfMonth | number（1–31） | 実行日 |
| isEnabled | boolean | 有効/無効 |
| createdAt / updatedAt | timestamp | |

### 8.4 クエリとインデックス

| 対象 | クエリ | 必要なインデックス |
|---|---|---|
| 取引一覧（`TransactionsContext`） | `transactions` where `userId == uid` orderBy `date desc` | **複合インデックス `userId ASC, date DESC`（要手動作成）** |
| 定期取引（`useRecurringTransactions`） | `users/{uid}/recurringTransactions` orderBy `dayOfMonth asc` | 単一フィールド（自動） |
| 設定シード判定（`SettingsContext`） | `transactions` where `userId == uid` limit 1 | 単一フィールド（自動） |

- 取引一覧の複合インデックスはリポジトリで管理していない（`firestore.indexes.json` は無く、`firebase.json` にも `indexes` の指定が無い）。新しい Firebase プロジェクトで初回にアプリを開くと、Firestore が `failed-precondition` エラーとともにインデックス作成用リンクをブラウザコンソールに出すので、そのリンクから Firebase Console で作成する運用になっている。
- 取引は**ユーザーの全期間分を1本のリスナーで購読**し、月やカテゴリの絞り込みはクライアント側のメモリ上で行う。ページネーションは無い。個人利用（数千件規模）を前提としており、件数が増えると初期ロードと再計算のコストが線形に増える（[15. 既知の課題](#15-既知の課題今後の検討事項) 参照）。

### 8.5 データのライフサイクル

- **作成**: 取引・定期取引はクライアントが `createdAt` / `updatedAt` を付与して作成する。設定ドキュメントは初回ログイン時に自動シードされる。
- **更新**: 部分更新（`updateDoc` / `setDoc(merge)`）。設定ドキュメントは配列を含むため、パッチを手元の現在値に重ねて全体を書き戻す。**競合検出・バージョン照合は行わない**ため、複数端末で同時に設定を変更すると後勝ちで上書きされる（初回シードのみ `runTransaction` で二重作成を防いでいる）。
- **日時の基準**: 取引日の月判定・表示は**端末のローカルタイムゾーン**（`dayjs` / `toLocaleDateString('ja-JP')`）で行い、JST 固定ではない。`createdAt` / `updatedAt` はクライアントの時計で付与し、サーバー時刻（`serverTimestamp`）は使わない。
- **削除**: 取引・定期取引はいずれも**物理削除**（論理削除フラグは持たない）。削除した取引は復元できない。
- **保持期間**: 無期限。自動アーカイブ・自動削除は行わない。
- **アカウント削除**: アプリ内に機能は無い。Firebase Console から Authentication のユーザーを削除しても Firestore 上の `transactions` / `users/{uid}` は残るため、完全に消すには手動で Firestore のデータも削除する必要がある。
- **エクスポート**: 取引のみ CSV で出力できる。設定・定期取引はエクスポート対象外（[11.7 バックアップ・リストア](#117-バックアップリストア) 参照）。

## 9. 状態管理方針

- グローバル状態は `AuthContext` / `SettingsContext` / `TransactionsContext` の3つの React Context のみ（`src/app/layout.tsx` でラップ）。
- 表示中の年月は state ではなく URL クエリ（`?month=`）に持つ。タブの選択も URL パスが正とする。
- グラフの表示設定はユーザー設定ドキュメントに保存する（`localStorage` は PWA で消えることがあるため使わない）。

## 10. 認証・認可

- **認証方式**: Firebase Authentication のメール/パスワードのみ（他プロバイダなし）。
- **新規登録時のパスワード要件**: 10文字以上（Firebase 既定の6文字よりアプリ側で引き上げ）。
- **エラーメッセージ**: 「未登録」と「パスワード誤り」を区別しない（アカウント列挙耐性）。
- **認可**: サーバー側 API が無いため、**Firestore セキュリティルールのみ**がアクセス制御を担う。取引データはクライアント側で所有者チェックをしておらず、検証はルール側の責務。
- **セッション**: Firebase Auth 既定の永続化（IndexedDB 優先、利用不可なら `localStorage` / `sessionStorage`）に従い、明示的なタイムアウトは設けていない。ログアウトはヘッダーメニューから行う。

### 10.1 Firestore セキュリティルールの要約

| パス | 読取 | 作成 | 更新 | 削除 |
|---|---|---|---|---|
| `transactions/{id}` | `userId == 自分` | `userId == 自分` かつ [必須項目の検証](#81-transactionstransactionid-トップレベルコレクション) | 同左 かつ `userId` の変更禁止 | `userId == 自分` |
| `users/{uid}/**` | `uid == 自分` | 同左 | 同左 | 同左 |
| 上記以外 | 拒否 | 拒否 | 拒否 | 拒否 |

- `users/{uid}/**` 配下はスキーマ検証を行わない（ログインしていれば自分の配下に任意の構造を書ける）。
- ルールの正本は `firestore.rules`。変更後は `firebase deploy --only firestore:rules` で反映しないと本番に効かない。

### 10.2 未対応の認証機能

以下はアプリの画面から行えない。

| 機能 | 現状の代替手段 |
|---|---|
| パスワードリセット（再設定メールの送信） | Firebase Console の Authentication からユーザーごとに再設定メールを送る |
| アカウント削除・メールアドレス変更 | Firebase Console で操作する。Firestore のデータは残る（[8.5](#85-データのライフサイクル)） |
| メールアドレスの確認（verification） | 無し（未確認のまま利用できる） |
| 多要素認証、ソーシャルログイン | 無し（Console の設定だけでは使えず、アプリ側の実装が必要） |

## 11. 非機能要件

### 11.1 セキュリティ

- Firestore ルール（`firestore.rules`）でユーザーは自分のデータのみ読み書き可能。ルール変更時は `firebase deploy --only firestore:rules` での反映が必須（忘れると本番ルールが古いまま残る）。
- クライアントに公開してよい環境変数は `NEXT_PUBLIC_*` のみ。`.env.local` はコミットしない。
- セキュリティヘッダーは `next.config.ts` に集約。CSP は現状 Report-Only。
- 家計データを `console` に出力しない（本番ビルドは `console.error` 以外を除去）。
- App Check（reCAPTCHA v3）は任意導入（未強制運用を推奨）。

### 11.2 パフォーマンス・可用性

- Turbopack による開発時ビルド高速化。
- Firestore のリアルタイムリスナーで即時反映（ポーリング無し）。
- デプロイは Vercel の自動ビルド・自動デプロイ。ロールバックは Vercel ダッシュボードから「Promote to Production」で行う。
- 本番反映確認用に、画面下部にビルド時のコミットSHA（先頭7桁）を表示する。

### 11.3 レスポンシブ / PWA

- モバイル判定は共通ブレークポイント `768px`（`useMediaQuery('(max-width: 768px)')`）。
- タップ領域48px以上、入力フォント16px以上（iOSのズーム防止）。ピンチズームは許可する（`maximumScale: 5`）。
- `public/manifest.json` によりホーム画面への追加に対応（`display: standalone`、縦向き固定、ショートカット「年間振り返り」）。
- **Service Worker**（`public/sw.js`）は本番ビルドでのみ登録し、開発時は既存の登録を解除する。キャッシュ戦略は次のとおり。
  - ページ遷移（navigate）: ネットワークファースト。失敗時のみキャッシュ（無ければ `/`）にフォールバックする。キャッシュファーストにするとデプロイ後も古い画面が出続けるため。
  - ページ遷移以外の自オリジン GET リクエスト全般（JS / CSS / 画像などの静的アセットを含む。拡張子やコンテンツ種別による限定は無い）: キャッシュファースト + バックグラウンド更新（stale-while-revalidate）。
  - 他オリジン（Firebase 等）と GET 以外: キャッシュしない。
  - キャッシュ名 `kakeibo-app-vN` を変えると activate 時に旧キャッシュを削除する。戦略を変えたら必ず N を上げる。
- インストール案内は `beforeinstallprompt` 発火時にモーダルで表示し、「後で」を選ぶと24時間は再表示しない（`localStorage` の `pwa-dismissed`）。
- モバイルはスワイプ操作（framer-motion）で月・日を移動できる。

### 11.4 バージョニング

- Semantic Versioning。`package.json` の `version` を唯一の情報源とし、画面下部に表示する。
- ユーザーに見える変更を行った PR では必ずバージョンを更新し、`docs/CHANGELOG.md` の先頭に変更点を追記する。

### 11.5 エラーハンドリング方針

- **ユーザー操作に起因する書き込み失敗**（取引・設定・定期取引の保存、削除）は、`try/catch` で捕捉して Mantine の通知（赤）で「〜に失敗しました。もう一度お試しください。」と表示する。自動リトライは行わない。例外として CSV インポートは、読み込み・解析・書き込みのどの段階の失敗も「ファイルの読み込みに失敗しました」にまとめる。
- **リアルタイムリスナーのエラー**（`onSnapshot` の error コールバック）は `console.error` に出してローディングを解除するだけで、**画面上には通知しない**。ルール不一致やインデックス未作成のときは「データが空」に見えるため、切り分けは [`deployment.md`](./deployment.md#トラブルシューティング) に従う。
- **不完全な取引ドキュメント**（`type` / `amount` / `category` / `date` のいずれかが欠ける）は一覧から除外し、ドキュメント ID と欠落フィールド名だけを `console.warn` に出す（取引の中身は出さない）。
- **認証エラー**は Firebase のエラーコードを日本語メッセージに変換して表示する。未知のコードは汎用メッセージにまとめる。
- React のエラーバウンダリ（`error.tsx`）は置いておらず、描画中の例外は Next.js 既定のエラー画面になる。

### 11.6 ログ・監視

- アプリケーション側のエラー監視サービス（Sentry 等）やアクセス解析は**導入していない**。
- 本番ビルドでは `console.error` 以外の `console` 出力を除去する。`console.error` にも取引の中身を渡さない。
- 確認できるログは以下のみ。
  - Vercel: ビルドログ・デプロイ履歴（ランタイムログは静的配信のため実質無い）
  - Firebase Console: Authentication のユーザー一覧、Firestore の使用量（読み取り/書き込み回数）
  - ブラウザの開発者ツール: CSP 違反（Report-Only のためコンソールに出るだけで、送信先は設定していない）
- 死活監視・アラートの仕組みはリポジトリ内には無い（外部サービスでの監視を別途設定しているかは本書の範囲外）。

### 11.7 バックアップ・リストア

- Firestore 側の自動バックアップ（PITR / スケジュールバックアップ）の設定はリポジトリでは管理しておらず、Firebase Console 側で有効化しているかは本書では確認していない。**未設定であれば、誤削除や誤インポートからの復旧手段はユーザーが手動で取った CSV に限られる**。
- 推奨運用: 月1回程度、ヘッダーメニューの「CSV インポート/エクスポート」から全取引を CSV に保存する（[`機能仕様書.md`](./機能仕様書.md#11-csv-エクスポート--インポート) 参照）。
- **CSV は完全なバックアップではない**。
  - 取引のみが対象。設定（カテゴリ・役割・支払方法・予算・グラフ設定）と定期取引は含まれず、復元できない。
  - 取引の ID・`createdAt` / `updatedAt` は再生成され、`transactionType` / `affectsExpense` は取り込み時の設定から再導出される。
  - 改行を含むメモは、インポート時に行単位で分割されるため正しく往復できない。
  - 文字数（メモ200文字・名称50文字）・金額（10億円）・件数（5,000行）・ファイルサイズ（2MB）の上限を超えた分は切り詰め・スキップされる。
- CSV インポートは**追記**であり既存取引と重複チェックしない。同じ CSV を2回取り込むと取引が二重になる。復旧の際は先に既存取引を削除してから取り込む。

### 11.8 アクセシビリティ

- 明示的な準拠レベル（WCAG 等）は定めていない。
- アイコンのみのボタンには `aria-label` を付与する方針だが、徹底はされていない（テーマ切替・メニュー・取引の削除・予算入力には付与済み。定期取引管理の編集・削除ボタンなど未対応箇所がある）。
- ライト / ダークテーマの両方で読めるよう、色はデザイントークン（CSS 変数）とユーザー設定のパレット（ライト/ダーク2色）から解決する。
- ピンチズームを禁止しない。金額は `tabular-nums` で桁揃えする。
- キーボード操作・スクリーンリーダーでの網羅的な検証は行っていない。

### 11.9 データ保護・プライバシー

- 保存する個人データはメールアドレス（Firebase Auth）と家計データ（取引・設定）のみ。氏名・住所・口座番号などは扱わない。
- データの保管場所は Firebase プロジェクト作成時に選んだリージョンに従う。
- 第三者へのデータ提供・外部解析ツールへの送信は行わない。
- 家計データはブラウザの `console` に出力しない（[11.1](#111-セキュリティ)）。

## 13. 制約・前提事項

- 自動テストスイートが存在しない。変更後は lint・型チェック・手動動作確認で品質を担保する。
- 実際の銀行口座残高（現金の増減そのもの）は記録・計算しない。アプリが扱うのは「収支」（選択月の収入−支出、[2. 用語定義](#2-用語定義) 参照）であり、クレジットカードの支出は購入月の支出として即座に反映される。
- カード還元ポイントの計算・年収の額面推定はいずれも**概算**であり、公式な帳票（源泉徴収票等）の代替にはならない。前提条件は [`user-guide.md`](./user-guide.md) に明記されている。
- カテゴリを削除・リネームしても既存取引のカテゴリ名は変わらない（データの後方互換のため）。
- 家族・複数ユーザーでの家計簿共有機能は無い（1アカウント=1家計簿）。
- Firebase の無料枠（Spark）を前提としており、Firestore の読み取り回数は「ログインごとに全取引を1回読む + 変更差分」で消費する。取引数が増えるほど1ログインあたりの読み取り回数が増える。

## 14. 開発・リリースプロセス

詳細はリポジトリ直下の `AGENTS.md` を正とする。ここでは仕様として押さえるべき点のみ記す。

| 項目 | 内容 |
|---|---|
| ブランチ戦略 | `main` へ直接コミットしない。フィーチャーブランチ → PR → `main` へマージ |
| レビュー | PR 単位。Vercel の Preview デプロイで動作確認する |

| リリース | `main` へのマージ = 本番リリース（Vercel が自動デプロイ）。リリース承認フローや定期リリース日はリポジトリ上の仕組みとしては無い |
| バージョン更新 | ユーザーに見える変更を含む PR で `package.json` の `version` と `docs/CHANGELOG.md` を同時に更新する |
| Firestore ルール | `firestore.rules` を変更した PR は、マージ後に `firebase deploy --only firestore:rules` を手動で実行する（Vercel は反映しない） |
| Service Worker | `public/sw.js` のキャッシュ戦略を変えたら `CACHE_NAME` のバージョンを上げる |
| ロールバック | Vercel ダッシュボードから旧デプロイを「Promote to Production」 |
| コミット | 日本語、Conventional Commits 形式のプレフィックス |

| 6 | パスワードリセット・アカウント削除の機能が無い（[10.2](#102-未対応の認証機能)） | 運用者が Firebase Console で手動対応する |

| 11 | 設定ドキュメントの更新に競合検出が無い（[8.5](#85-データのライフサイクル)） | 複数端末で同時に設定を変更すると後勝ちで上書きされる |
| 12 | リアルタイムリスナーが取引を全件購読し、`createdAt` / `updatedAt` はクライアント時計に依存（[8.4](#84-クエリとインデックス) / [8.5](#85-データのライフサイクル)） | 端末の時計がずれていると作成日時もずれる |
